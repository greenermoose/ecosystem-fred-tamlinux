Software Packaging & Delivery

← Back to Ecosystem Index

Traditional operating systems overwrite files in global directories (/usr/bin), making upgrades destructive, rollbacks difficult, and development fragile. Tamlinux solves this with a dual-track packaging architecture.

1. The Desktop Delivery Track: Nix & Home Manager

Tamlinux packages its own desktop shell, plugins, commands (like tam), and user configuration using Nix and Home Manager (Decisions D114, D132):

  • Immutable Store Paths: Every package is built into an isolated path under /nix/store/<hash>-<name>. Dependencies are locked via flake.lock in tamlinux-packages.
  • Identical Deployments for Test and Run: In Decision D132, Fred established that testing a candidate assembly and running a daily driver use the exact same deployment mechanism.
  • Instant, Guaranteed Rollback: If a newly deployed desktop version exhibits an issue, rolling back to the previous generation is instantaneous (home-manager switch --generation <N>). Files are never corrupted or overwritten.
  • Portable Grafting (D72): Because Nix packages are self-contained, the Tamlinux desktop can be grafted cleanly onto Arch, Void, or Debian hosts without altering the host's base package database.

2. The Base OS Track: Native Package Managers

Low-level operating system primitives (the Linux kernel, DRM/KMS drivers, Mesa, C runtimes, and firmware) remain managed by the native host package manager:

  • Pacman (Arch Linux today): Written in C (libalpm), Pacman is fast and transparent. In ecosystem-fred-tamlinux, repository precedence is leveraged so that the local [local-patches] repository takes priority over upstream Arch builds.
  • XBPS (Void Linux tomorrow): Fast C implementation featuring atomic transactions and clean xbps-src templates. Tamlinux will maintain its own signed XBPS repository for native Void packages.

3. Safe Patching vs. Silent Overwriting

When Tamlinux must carry a patched build of third-party software (such as Aquamarine or Hyprland), it never modifies files in /usr directly and never uses silent pinning tricks like IgnorePkg:

  1. The fix is developed on a public Git fork off the upstream release tag.
  2. Patches are exported cleanly via git format-patch.
  3. The package is built with a local release suffix (e.g. pkgrel <arch>.N) into [local-patches].
  4. A post-transaction Pacman hook (50-*.hook) monitors updates and loudly warns when upstream ships a newer version, triggering a rebase or clean retirement.
